# ТЗ: GPS API для Tracker

Контракт HTTP API, который ожидает мобильное приложение Tracker.
Документ можно использовать как ТЗ для реализации на новом сервере.

---

## 1. Общие требования

| Параметр | Значение |
|---|---|
| Base URL | `http://169.58.181.154` |
| Протокол | HTTPS (рекомендуется), HTTP допустим для тестов |
| Формат | JSON, UTF-8 |
| Авторизация | HTTP Basic Auth |
| Успех для клиента | любой HTTP **2xx** (обычно `200`) |
| Таймаут auth | 10 секунд |
| Таймаут coordinates | 20 секунд |
| Размер пакета | до **250** точек в одном `POST` |
| Интервал отправки с телефона | раз в **10 минут** |

### Поведение клиента

1. GPS-точки пишутся в локальную SQLite на телефоне каждые ~5 секунд.
2. Раз в 10 минут приложение отправляет накопленные точки пакетами.
3. Успехом считается **только HTTP 2xx**.
4. При любой другой ошибке / таймауте / сети точки остаются в очереди и будут отправлены повторно.
5. Если сервер уже сохранил точки, но вернул не-2xx или ответ пришёл позже 20 сек — клиент отправит тот же пакет снова.

### Авторизация

```http
Authorization: Basic base64(login:password)
```

Сервисная учётка должна:
- не блокироваться после нескольких неверных попыток;
- иметь стабильный доступ к обоим методам ниже.

## 2. API: статус пользователя

Нужен, чтобы сервер мог включать/выключать GPS у конкретного агента.

### Запрос

```http
GET /hs/data/auth?user_id={userId}
Authorization: Basic <base64>
Accept: application/json
```

Пример:

```http
GET /hs/data/auth?user_id=21696
```

### Успешный ответ

```http
HTTP/1.1 200 OK
Content-Type: application/json
```

```json
{
  "gps": true,
  "from": "0001-01-01T08:00:00",
  "to": "0001-01-01T18:00:00",
  "name": "Иванов Иван"
}
```

### Поля ответа

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `gps` | `boolean` | да | `true` — трекинг разрешён. `false` — приложение останавливает GPS и не отправляет координаты |
| `from` | `string` | нет | Начало рабочего окна. Формат как в примере |
| `to` | `string` | нет | Конец рабочего окна |
| `name` | `string` | нет | ФИО пользователя для отчётов |
| `user_name` | `string` | нет | Альтернативное имя поля ФИО |
| `full_name` | `string` | нет | Альтернативное имя поля ФИО |
| `fio` | `string` | нет | Альтернативное имя поля ФИО |
| `agent_name` | `string` | нет | Альтернативное имя поля ФИО |

Клиент читает ФИО из первого непустого поля:
`name` → `user_name` → `full_name` → `fio` → `agent_name`.

### Ошибки

| HTTP | Поведение клиента |
|---|---|
| не `200` | статус игнорируется, GPS работает по кэшу |
| сеть / таймаут | то же |

## 3. API: приём GPS-точек

Основной метод. Клиент шлёт батч координат.

### Запрос

```http
POST /hs/data/coordinates
Content-Type: application/json
Authorization: Basic <base64>
Accept: application/json
```

### Body

Тело — JSON **массив** объектов (не один объект).

```json
[
  {
    "user_id": "21696",
    "latitude": "40.2682455",
    "longitude": "69.5641146",
    "date": "2026-08-08T17:12:30"
  },
  {
    "user_id": "21696",
    "latitude": "40.2682258",
    "longitude": "69.5642303",
    "date": "2026-08-08T17:12:37"
  }
]
```

### Поля точки

| Поле | Тип | Обязательно | Формат | Описание |
|---|---|---|---|---|
| `user_id` | `string` | да | `"21696"` | ID агента из приложения |
| `latitude` | `string` | да | `"40.2682455"` | Широта. Важно: именно **string**, не number |
| `longitude` | `string` | да | `"69.5641146"` | Долгота. Именно **string** |
| `date` | `string` | да | `YYYY-MM-DDTHH:mm:ss` | Время фиксации на телефоне, без timezone |

Пример формата даты: `2026-08-15T11:00:00`.

### Особый сигнал: GPS выключен на устройстве

Тот же endpoint и формат, но координаты нулевые:

```json
[
  {
    "user_id": "21696",
    "latitude": "0.00000",
    "longitude": "0.00000",
    "date": "2026-08-15T11:00:00"
  }
]
```

`latitude = "0.00000"` и `longitude = "0.00000"` означают, что геолокация на телефоне отключена. Это не реальная точка маршрута.

### Успешный ответ

Любой HTTP **2xx**. Рекомендуется:

```http
HTTP/1.1 200 OK
Content-Type: application/json
```

```json
{
  "ok": true,
  "accepted": 2
}
```

Тело ответа клиент почти не парсит. Критичен именно статус-код.

### Ошибки

| HTTP | Когда использовать |
|---|---|
| `400` | Невалидный JSON / нет обязательных полей |
| `401` / `403` | Ошибка авторизации / нет доступа |
| `429` | Слишком частые запросы |
| `500` | Внутренняя ошибка сервера |

### Критичное правило

Если точки уже записаны в БД — всё равно верните **200**.

Иначе телефон будет считать отправку неуспешной и пришлёт тот же пакет повторно.

## 4. Рекомендации по реализации на новом сервере

1. **Идемпотентность**  
   Уникальный ключ: `(user_id, date)`.  
   Повторная отправка той же точки не должна создавать дубль.

2. **Скорость ответа**  
   Желательно < 3 секунд даже на пакет из 250 точек.  
   Жёсткий лимит клиента — 20 секунд.

3. **Атомарность пакета**  
   Либо принять весь пакет и вернуть 200, либо откатить и вернуть ошибку.  
   Нельзя «молча» принять часть и ответить ошибкой.

4. **Авторизация**  
   Не блокировать сервисный логин после нескольких ошибок пароля.  
   Для нового сервера лучше сразу HTTPS + отдельный API-user.

5. **Пути**  
   Можно оставить `/hs/data/auth` и `/hs/data/coordinates` — тогда в приложении меняется только base URL.  
   Если пути будут другие (`/api/v1/gps/...`) — нужно синхронно поправить клиент.

6. **Хранение**  
   Минимум полей в таблице точек:
   - `user_id`
   - `latitude`
   - `longitude`
   - `captured_at` (`date` из запроса)
   - `received_at` (время приёма на сервере)
   - опционально `raw_payload`

## 5. Примеры проверки (curl)

### Auth

```bash
curl -u 'API_USER:API_PASSWORD' \
  -H 'Accept: application/json' \
  'https://YOUR_DOMAIN/hs/data/auth?user_id=21696'
```

Ожидание: HTTP 200 и JSON с `"gps": true/false`.

### Coordinates

```bash
curl -u 'API_USER:API_PASSWORD' \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json' \
  -X POST 'https://YOUR_DOMAIN/hs/data/coordinates' \
  -d '[
    {
      "user_id": "21696",
      "latitude": "40.2682455",
      "longitude": "69.5641146",
      "date": "2026-08-15T11:00:00"
    }
  ]'
```

Ожидание: HTTP 200.

### Повтор той же точки

Повторный `POST` с тем же `user_id` + `date` должен:
- вернуть 200;
- не создать второй дубль в БД.

## 6. Что менять в мобильном приложении после готовности API

В `lib/services/server_service.dart`:

```dart
static const String _baseUrl = 'https://YOUR_DOMAIN';
static const String _username = 'API_USER';
static const String _password = 'API_PASSWORD';
```

Пути `/hs/data/auth` и `/hs/data/coordinates` можно не менять, если бек реализует их 1-в-1.

---

## 7. Краткий чеклист приёмки

- [ ] `GET /hs/data/auth?user_id=...` возвращает 200 и `gps`
- [ ] `gps: false` останавливает трекинг на телефоне
- [ ] `POST /hs/data/coordinates` принимает массив до 250 точек
- [ ] `latitude` / `longitude` принимаются как строки
- [ ] `date` принимается в формате `YYYY-MM-DDTHH:mm:ss`
- [ ] Успех всегда HTTP 2xx
- [ ] Ответ быстрее 20 секунд
- [ ] Повтор той же точки не создаёт дубль
- [ ] `0.00000 / 0.00000` сохраняется как сигнал «GPS выключен»
- [ ] Basic Auth работает стабильно, без блокировки учётки
